Создавай **готовый к показу черновик** SEO-ориентированного сайта детского коррекционного центра с компактной админкой и конструктором визиток. Не превращай проект в SaaS/CRM. Единственная онлайн-заявка — **обратный звонок**. Нет записи в свободные слоты, личных кабинетов родителей, онлайн-оплаты или расписания.

Репозиторий уже инициализирован; не уничтожать `.git` или пользовательские файлы. Учитывай, что `yarn init` и `tsc --init` создали предварительные файлы, которые можно корректно адаптировать под новый проект.

## Архитектура

- Nuxt 4 + Vue 3 + TypeScript; Tailwind CSS и Less, Element Plus преимущественно для админки.
- SEO-first: публичный контент должен быть в HTML **без исполнения JS и WebSocket**. Выбери SSG как основу, SSR только обоснованно. Админка может быть CSR.
- Реализуй чёткий механизм публикации контента из БД в публичные страницы: контролируемая пересборка/инвалидация, понятный статус публикации и обработка ошибок. Не имитируй динамическое обновление SSG.
- Минимальный backend, предпочтительно NestJS + Fastify; SQLite с миграциями. Без очередей, микросервисов, Redis и иных избыточных элементов.
- WebSocket RPC для админки и интерактивных операций, HTTP для файлов и необходимых SEO/служебных запросов. Не делай WebSocket обязательным при открытии публичной страницы.
- Заявки должны сохраняться даже при сбое имитации уведомления; email пока **только mock**, никаких реальных писем.
- Не придумывай данные, которых нет. Для незаполненных материалов используй помеченные демонстрационные записи.

## Правила Vue-компонентов

Предпочтение владельца проекта — **Options API с `setup()` только для состояния и функциями в `methods`**. Скрипт компонента выноси в отдельный файл `script.ts`, стили — в `style.less`, шаблон — в `index.vue` (там, где у компонента есть собственные стили/логика). Не используй `<script setup>` для пользовательских компонентов. Пример подхода:

```ts
import { ref } from 'vue';

export default {
    setup() {
        return {
            title: ref<string>('')
        };
    },
    methods: {
        save(this: any) {
            // логика действия
        }
    }
};
```

Не добавляй `data()`. Не прячь бизнес-функции в `setup()`. Не сокращай значимые имена переменных до одной буквы. Не создавай лишние абстракции, интерфейсы и типы без практического выигрыша. Вынужденные Nuxt composables/plugins и серверные модули делай нативным для Nuxt способом, но не переписывай все UI-компоненты на Composition API.

## Процесс работы

1. Перед кодом осмотри текущее состояние репозитория; не делай вид, что отсутствующие файлы уже существуют.
2. Реализуй законченными вертикальными срезами. После каждой крупной части запускай доступные сборку, проверку типов и тесты; исправляй ошибки.
3. Пиши реальные работающие маршруты, компоненты, обработчики, сохранение данных и экспорт; не оставляй псевдофункции и неработающие кнопки.
4. Для публичных страниц проверяй **результирующий HTML**, а не только настройки Nuxt; не допускай зависимости контента от WebSocket.
5. Не запускай реальные отправки писем, покупку домена, внешние публикации или передачу персональных данных без явного разрешения.
6. Для тестирования применяй фиктивные персональные данные. Не коммить секреты, реальные заявки, БД, загруженные фотографии детей.
7. Поддерживай `.gitignore` и точные команды запуска в `README.md`; сохраняй типизированные и воспроизводимые миграции/seed.
8. По окончании задания кратко перечисли **что реально работает**, какие команды и тесты запущены, какие материалы ожидаются от заказчика и какие пункты остались незавершёнными. Не объявляй работу готовой по одним лишь созданным файлам.
